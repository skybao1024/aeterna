# I02 — Cryptography and Secure-Storage Risk Prototype

## Objective

Prototype and independently test the cryptographic building blocks required by
Aeterna's master-password path, delayed-recovery path, device request signing,
and macOS secure storage.

This iteration must produce security-review evidence. It must not freeze a
production vault format, implement a vault database, expose secrets to React, or
claim that passing tests constitutes a cryptographic audit.

## Authoritative cryptographic requirements

- VDK: a 256-bit value generated by an operating-system CSPRNG.
- Master KEK: 256 bits derived from the master password using Argon2id with an
  explicit algorithm version and explicit, versioned parameters.
- Master salt: at least 128 random bits and never reused as a fixed project
  constant.
- Recovery KEK: 256 bits derived with HKDF-SHA-256 from ERC as input keying
  material, SRS as salt, and versioned context containing vault and device IDs.
- ERC: at least 128 bits generated by a CSPRNG, not selected as a password or
  PIN, encoded for manual handling with error detection.
- SRS: an independent 256-bit random value per device recovery record.
- VDK wrapping: AES-256-GCM with a unique random nonce, a full authentication
  tag, versioned associated data, and fail-closed authentication errors.
- Device request key: a unique device signing key whose private material is kept
  in operating-system secure storage; the prototype evaluates Ed25519.
- Passwords, ERC, VDK, KEKs, SRS, private keys, nonces paired with secrets, and
  plaintext test operations must never enter logs, panic text, error messages,
  snapshots, the clipboard, command-line arguments, or the WebView.

## Mandatory decision and dependency checkpoint

Before adding a cryptography, randomness, secret-memory, encoding, signing, or
Keychain dependency, create
`docs/research/I02-crypto-dependency-proposal.md`. Evaluate at least:

- Argon2id implementation;
- AES-256-GCM implementation;
- HKDF-SHA-256 and SHA-256 implementations;
- operating-system CSPRNG interface;
- Ed25519 signing implementation;
- secret-memory and zeroization types;
- ERC encoding and checksum implementation; and
- macOS SecItem/data-protection Keychain binding.

For each candidate record:

- exact proposed version and enabled features;
- repository owner, maintenance activity, release recency, and known audit or
  review evidence;
- license and transitive dependency impact;
- unsafe-code footprint and platform support;
- permissions, entitlements, storage, and runtime network behavior;
- serialization or interoperability implications;
- alternatives considered and reason for rejection; and
- whether the dependency is runtime, macOS-only, test-only, or build-only.

The proposal must also recommend, in one approval round:

1. an ERC representation and checksum strategy;
2. a canonical, versioned AAD encoding for master and recovery wrapping;
3. the macOS Keychain item class and attributes, including data-protection
   Keychain selection, accessibility, explicit non-synchronization, service and
   account naming, and update/delete semantics; and
4. the benchmark policy used to recommend—not silently freeze—Argon2 settings.

Ask the user for explicit approval of this combined proposal before changing
`Cargo.toml`, lockfiles, cryptographic formats, or Keychain behavior. A plausible
default or an existing transitive crate is not approval. Dependency-free types,
test planning, and documentation may proceed while waiting.

## Required architecture

Separate these modules and responsibilities:

1. **Secret types:** fixed-size VDK, KEK, ERC entropy, SRS, salt, nonce, and
   signing-secret wrappers. Secret types use redacted formatting, minimize
   cloning, and zeroize on drop where supported.
2. **Primitive adapters:** small wrappers around reviewed crates. They enforce
   exact algorithms, sizes, parameter bounds, and fixed safe errors. They do not
   expose generic algorithm selection to callers.
3. **Key hierarchy:** master and recovery wrapping/unwrapping operations using
   typed inputs and canonical AAD.
4. **Device signing:** key generation, public-key export, signing, and
   verification. The signing payload protocol itself belongs to I09/I10 and is
   not designed here.
5. **Secure-storage port:** a narrow interface for storing, retrieving,
   replacing, and deleting device private material.
6. **macOS Keychain adapter:** the smallest native implementation of the port,
   behind `cfg(target_os = "macos")`, with explicit unsupported behavior on
   other platforms.
7. **Prototype harness and benchmarks:** development-only commands using
   internally generated synthetic material. They must never accept secrets in
   command-line arguments or print secret values.

The React/WebView layer receives no secret, key, raw crypto operation, generic
encrypt/decrypt command, or Keychain command. I02 should normally require no new
Tauri capability.

## Versioned prototype model

The prototype must make these values explicit rather than depending on crate
defaults:

- crypto format version;
- KDF algorithm and version;
- Argon2 memory, time, parallelism, and output length;
- salt and nonce lengths;
- AEAD algorithm and tag length;
- wrap purpose (`master-vdk` or `recovery-vdk`);
- canonical vault ID and device ID representation; and
- ERC format version.

Unknown versions, algorithms, purposes, sizes, or parameters outside approved
resource limits must be rejected before expensive allocation or derivation.
This is required to prevent a malicious future vault header from turning KDF
parameters into a memory or CPU denial of service.

Project-specific deterministic fixtures may be encoded as documented JSON with
hexadecimal or another approved unambiguous binary representation. The fixture
is a test interchange format, not automatically the production vault
serialization format.

## Implementation stages

### Stage A — Baseline, standards, and approval

1. Run the pinned I00 verification suite.
2. Read the standards and upstream documentation relevant to each primitive.
3. Produce the combined dependency and design proposal.
4. Ask for explicit user approval and record the answer.
5. Do not start cryptographic implementation or modify dependency manifests
   before approval.

### Stage B — Known-answer primitive tests

Implement minimal reviewed adapters and pass published known-answer tests for:

- Argon2id version 0x13;
- HKDF-SHA-256 extract-and-expand;
- AES-256-GCM encryption, AAD authentication, and authentication failure; and
- Ed25519 public-key derivation, signature generation, and verification.

The tests must compare bytes to published vectors without logging derived
secrets. Do not replace a published-vector mismatch by regenerating the expected
value from the same implementation.

### Stage C — Aeterna dual-path prototype

Using synthetic inputs, prove:

1. A random VDK can be wrapped and unwrapped through a master-password-derived
   KEK.
2. The same VDK can be independently wrapped and unwrapped through the ERC + SRS
   recovery path.
3. Changing the master password only changes the master wrapper; it does not
   change the VDK or require re-encrypting hypothetical vault data.
4. ERC without SRS cannot derive the correct recovery KEK.
5. SRS without ERC cannot derive the correct recovery KEK.
6. Wrong password, ERC, SRS, vault ID, device ID, purpose, version, nonce, tag,
   ciphertext, or AAD fails closed and returns a fixed non-sensitive error.
7. Distinct wrappers use distinct nonces and purpose-specific AAD.
8. Invalid or hostile KDF parameters and malformed lengths are rejected before
   costly work.

Use dependency injection only for deterministic tests. Production constructors
must obtain randomness from the approved operating-system CSPRNG and must not
accept a caller-supplied nonce.

### Stage D — ERC handling prototype

Generate at least 128 bits of entropy with the approved CSPRNG and encode it with
the approved language-independent, versioned error-detection format. Test:

- round trip and checksum verification;
- single-character and selected transposition errors;
- rejected ambiguous, truncated, overlong, mixed-format, or unknown-version
  input;
- normalization rules, grouping, and canonical display; and
- absence from clipboard APIs, logs, panic output, snapshots, and WebView data.

Do not implement word lists, translations, QR transport, printing, or final UX
in this iteration.

### Stage E — Device signing and macOS Keychain

Generate a synthetic device signing key, store only its private material through
the secure-storage port, and retain/export only the public key outside the
Keychain adapter. Exercise create, retrieve, sign, verify, replace, delete, and
not-found behavior.

The macOS prototype must evaluate Apple's SecItem API and data-protection
Keychain behavior. Unless the approved proposal says otherwise, the evidence
must explicitly determine:

- whether the item is non-synchronizable;
- whether access is limited to the unlocked device/session as intended;
- whether an entitlement, access group, or user prompt appears;
- how unsigned development, debug app, and unsigned release builds affect
  access continuity;
- how duplicate items, updates, deletion, and app restart behave; and
- whether a failed read ever falls back to a file, environment variable,
  SQLite, local storage, or another plaintext location. Such fallback is
  prohibited.

Use a development-only namespace and an internally generated synthetic key.
Clean up the prototype item at the end. Never inspect or enumerate unrelated
Keychain items, and never invoke the `security` CLI to print secret data.

### Stage F — Argon2 benchmark

Run a release-mode benchmark grid on the current Apple Silicon host. Vary memory,
time, and parallelism within safe bounds and record:

- macOS version and architecture;
- CPU model category without a machine identifier;
- median and tail latency across enough warm and repeated samples;
- configured and observed peak memory where measurable;
- thermal/power caveats and sample count; and
- a recommended versioned parameter profile with rationale.

The benchmark must use a fixed synthetic password and salt without printing
them. It must not run as part of ordinary unit tests or CI. The result is a G0
recommendation, not a production freeze.

### Stage G — Evidence and proposed ADR

Create:

- `docs/research/I02-crypto-dependency-proposal.md`;
- `docs/research/I02-crypto-results.md`;
- `docs/adr/0002-cryptographic-envelope-and-key-storage.md` with status
  `Proposed`;
- reviewed synthetic fixtures under a clearly named test-fixture directory; and
- updates to `docs/DEPENDENCIES.md` for every approved dependency.

The proposed ADR must include algorithms, explicit sizes, version fields, AAD
encoding, parameter bounds, ERC format, Keychain policy, memory limitations,
alternatives, migration/versioning expectations, and the exact items deferred
to G0 or independent security review.

Do not mark the ADR `Accepted`; G0 owns that decision.

## Required automated tests

At minimum, cover:

- every published primitive known-answer vector selected by the results report;
- deterministic Aeterna master and recovery wrapper fixtures;
- correct master and recovery unwrap paths;
- every wrong-input and tampering case listed in Stage C;
- KDF lower/upper bounds and hostile allocation parameters;
- nonce and salt lengths plus generated-value uniqueness over a bounded sample;
- ERC canonicalization and error-detection cases;
- device signing and modified-message/signature/public-key rejection;
- secret types' redacted `Debug` behavior and fixed error strings;
- zeroize-on-drop behavior to the extent the crate supports observable tests,
  with compiler-copy limitations documented rather than overclaimed;
- secure-storage fake behavior on all platforms;
- macOS Keychain create/read/replace/delete/not-found behavior in a dedicated
  manual or ignored integration harness; and
- explicit unsupported secure storage on non-macOS platforms.

Tests must not use `unwrap()`, `expect()`, or panic formatting in production
paths. Test failures must not print a secret buffer.

## Real-machine evidence matrix

| ID  | Scenario | Required result |
| --- | --- | --- |
| K01 | Create a development-only device key item | Succeeds without secret output |
| K02 | Restart the debug app and retrieve/sign | Same public key verifies the new signature |
| K03 | Retrieve using the wrong service/account identity | Not found; no fallback |
| K04 | Replace the item intentionally | New public key is used; old key no longer signs |
| K05 | Delete and retrieve | Not found; repeated delete is safely classified |
| K06 | Attempt access while the user session/Keychain is locked | Access is denied or unavailable according to the approved policy |
| K07 | Unlock and retry | Access recovers without regenerating or exporting the private key |
| K08 | Build/run the unsigned release prototype | Behavior and any prompt are recorded; no silent plaintext fallback |
| K09 | Inspect item metadata through the adapter | Non-synchronization and approved accessibility attributes are confirmed without reading unrelated items |
| K10 | Remove the prototype item and stop | No development test key remains |

The user performs operating-system lock/unlock and any credential entry. The
development task must never request, type, store, or record the user's password.

## Acceptance criteria

I02 is `Accepted` only when all of the following are true:

1. The dependency/design proposal received explicit approval before manifests,
   formats, or native storage behavior changed.
2. Every approved direct dependency is pinned, locked, documented, and uses only
   justified features.
3. Argon2id, HKDF-SHA-256, AES-256-GCM, and Ed25519 published known-answer tests
   pass independently of project-specific fixtures.
4. Master and recovery wrappers independently recover the same VDK, and all
   wrong-input/tamper/version/purpose cases fail closed.
5. ERC generation provides at least 128 bits of CSPRNG entropy and its approved
   canonical encoding detects the required input mistakes.
6. Randomness is never replaced by deterministic test randomness in production
   constructors, and callers cannot supply production AEAD nonces.
7. Argon2 parameters are explicit, bounded before allocation, benchmarked in a
   release build, and recorded as a recommendation rather than a hidden default.
8. Device signing passes generation, standard-vector, sign/verify, tamper, and
   public/private separation tests.
9. K01-K10 pass on the current macOS host and confirm the approved local-only
   Keychain behavior without a plaintext fallback.
10. Secret types, diagnostics, errors, panic behavior, fixtures, and source scans
    show no real or generated secret leakage to logs, command lines, WebView,
    clipboard, snapshots, or tracked artifacts.
11. Secret-memory lifetimes are minimized and zeroization limitations are stated
    accurately; the report does not claim impossible guarantees about compiler,
    swap, crash dump, or copied-buffer behavior.
12. Unknown crypto versions, algorithms, purposes, sizes, and hostile KDF
    parameters are rejected safely.
13. The Proposed ADR and results clearly identify everything that still requires
    independent security review or G0 approval.
14. `npm run check` and `npm run desktop:build` pass using the pinned toolchains.
15. No I03, vault persistence, UI, network, server, or production recovery work
    is included.

## Completion and blocking rules

Update the I02 row and progress log in `docs/DEVELOPMENT_PLAN.md` only after the
evidence is complete:

- mark `Accepted` only when every criterion passes;
- mark `Blocked` when approval is withheld, a standard vector fails, the
  approved dependency cannot meet the design, Keychain behavior violates the
  policy, a required real-machine scenario cannot be performed, or the pinned
  toolchain cannot run; and
- state the exact recovery action for each blocker.

End the development task with changed files, approved dependency decisions,
standard and project-vector results, Argon2 benchmark evidence, K01-K10 results,
permission and prompt observations, privacy scans, full verification commands,
remaining security-review questions, and the Proposed ADR recommendation.

Do not start I03 in the same task. Do not commit, push, publish, or deploy unless
the user explicitly requests it.
